# 本机语音链路性能排查（2026-09-08）

结论：连续通话的主要等待来自 LLM 完整结构化输出，以及前端 900 ms 结束检测。当前 TTS 的自然度、语速和停顿问题应单独优化；TTS 合成计算不是短句回复的最大延迟项。

## 环境和方法

- Windows Docker，Ryzen 7 5800X、16 GB RAM、RTX 4060 8 GB；Docker 共享内存上限约 7.71 GiB。
- `sim7600-console` 使用 CPU SenseVoice int8、Matcha Baker steps-3 + Vocos 22 kHz，生产配置 2 线程。
- `sim7600-ollama` 使用 `qwen3.5:4b`，`ollama ps` 显示 100% GPU、上下文 8192。测试时模型已经加载，没有刻意卸载或重启生产服务。
- 原服务代码基线 `5edd0f3`；本次只增加诊断脚本和报告，不修改模型、会话逻辑或部署参数。
- 重复运行两次合成实验；下表及 JSON 记录第二次。每种线程数首次调用后，再跑 3 种长度文本各 2 次；随后运行 4 轮真实本地 LLM 请求，包括更正。
- [原始合成测量](pipeline-profile-2026-09-08.json) 不包含用户会话内容。近期会话分析只报告匿名时长汇总，不上传录音或转写。

## 逐环节结果

| 环节 | 测量或配置 | 判断 |
| --- | --- | --- |
| 说完到触发提交 | VAD `redemptionMs=900` | 固定配置等待，不是浏览器端实测；还受 VAD 分帧/判定影响 |
| 最终 ASR | 近期会话后 3 轮 72–145 ms；首次 881 ms | 短句通常不是主瓶颈；更早会话首次可达约 4 s |
| LLM 首个可见草稿 | 合成正常答复轮 461–496 ms | 流式文本已较快出现 |
| LLM 完整、通过校验的结果 | 同 3 轮 2.04–2.46 s；近期会话 2.11–3.14 s | 热态主瓶颈，TTS 需等到此时 |
| TTS 合成 | 合成 2 线程热态 166–403 ms；近期会话 213–330 ms | 相比 LLM 小；句子越长越慢 |
| TTS 输出到浏览器 started 回报 | 近期 5 次 29–93 ms | 包含事件分发、下载/解码和回报网络时间；不是物理扬声器延迟 |
| 服务收到最终 ASR 请求到 started 回报 | 近期 4 轮 2.43–3.95 s | 不含此前收音、VAD 和上传；加 900 ms 可作约 3.33–4.85 s 的粗略预算，不能视为实测端到端延迟 |

模型推理细分（正常答复 3 轮，Ollama 内部计时）：

- prompt 977–1097 tokens，预填充 307–340 ms。
- 输出 107–136 tokens，解码 1.66–2.12 s，约 64 tokens/s。
- 最后一次可见回复文字变化在 559–697 ms，完整结果还需约 1.48–1.76 s；模型继续生成字段、证据、动作等结构化内容。
- 请求的 load duration 18–23 ms，说明本轮等待不是大模型冷加载。单轮均只有一次模型调用，没有修复重试放大时长。
- 已显示的草稿不能直接作为已确认答案播出，否则后续证据校验失败或修复会造成无法撤回的口头错误。

首次调用和热态必须分开看：第二次实验 2 线程引擎首次 TTS 2.00 s、ASR 1.57 s；生产近期首次 TTS 3.40 s。首次包含初始化，文件缓存可能已热，且不同线程实验顺序固定，不能据此比较冷启动线程优劣。历史记录还有开场 LLM 数十秒等待，现有事件不足以将其精确归因为加载、排队或其他原因。

## TTS 听感

用户明确反馈声音机械、语调不自然，以及语速/停顿不合适。当前是固定单人女声、`sid=0`、`speed=1.0`，应用没有语速或句间停顿控制，也没有独立的口语化表达层。Matcha 模型及 Vocos 配置与[官方中文示例](https://k2-fsa.github.io/sherpa/onnx/tts/pretrained_models/matcha.html)一致，不能简单归结为模型加载错误。

合成样本开头低能量段约 60–100 ms，结尾约 40–80 ms，没有发现秒级首尾空白。这个 RMS 阈值测量不能说明句中节奏是否自然。初始化出现 `Unknown token: shei2` 警告，需要以包含“谁”的专门样本复查发音，不能将其当作所有机械感的原因。历史 ASR 回环 CER 衡量可识别性，不等于人耳自然度。

线程实验热态 TTS 中位数：1 线程 413 ms、2 线程 261 ms、4 线程 193 ms。4 线程比当前配置减少约 26%（约 68 ms），但不会改善音色和韵律，不能单靠它解决用户体验；这里只是串行、少样本测试，还未验证通话并发 CPU 争用。

## 实时 ASR 的隐藏计算开销

当前每积累约 1.2 秒新音频就将整段前缀重新送给离线 SenseVoice。合成 24 秒片段的 20 个递增前缀累计识别耗时 8.81 s；最后完整片段单次 0.907 s，累计约为单次的 9.7 倍。实际前端仅允许一个预览在途，会跳过忙碌时的请求，所以该实验是固定前缀工作量测量，不是实录请求时序回放。

`LocalSpeech` 的预览 ASR、最终 ASR、TTS 共用一个锁。正在运行的预览即使前端已不再使用结果，也可能占锁；最终 ASR 或 TTS 必须等待。代码确认存在串行化，但本次没有单独记录锁等待，不能将 8.81 s 全部计入回复等待。长句是下一步需要重点验证的场景。

## 优化优先级

1. **先处理 LLM 输出成本**：在不削弱字段、否定、更正和证据校验的前提下，实验精简可重复的输出和提示词；比较生成 token 数、完整结果延迟及语义回归通过率。不要通过提前播出未校验草稿来换取速度。
2. **结束检测可配置并做真实对话测试**：比较 900/600/450 ms。名义等待可减少 300/450 ms，但必须测量中文停顿导致的误切句、数字被截断和更正句分裂，不能只追求最低数值。
3. **启动预热并显示就绪阶段**：将首次 ASR/TTS 初始化移到接听前，必要时预热 LLM。主要改善首轮；成本是启动更久和常驻内存，应与冷态明确区分。
4. **单独改善听感**：先提供语速和句间停顿配置、保持字段事实不变的口语化短句。用相同文本试听不同速度/停顿，评分自然度、节奏和清晰度。再评估其他音色或模型；本次没有安装或宣称替代模型更好。
5. **减少预览重复识别和锁争用**：记录锁等待，测试长句；考虑最终识别优先、预览节流，或评估真正流式 ASR。拆分 ASR/TTS 锁前需验证 CPU 并发和引擎安全性。
6. **线程数属于次要优化**：4 线程有实测收益，先进行并发实验再调整部署，预期收益是几十到百毫秒量级。

## 复现与验证

在服务空闲时执行（会与服务共享 CPU/GPU；只使用已有模型）：

```powershell
docker cp scripts/profile_pipeline.py sim7600-console:/tmp/profile_pipeline.py
docker exec sim7600-console python /tmp/profile_pipeline.py --models /models --output /data/profile-new-run --ollama-url http://ollama:11434
```

输出目录必须不存在，避免覆盖结果。输出包括 JSON 与 3 个合成 WAV；不读取实际会话。重新测量时使用不同目录，并记录模型版本和冷热状态。`first_draft_seconds` 记录应用收到非空回复草稿，而非模型底层首 token；内部 Ollama duration 单位是纳秒。

验证：现有 Python 测试 76 项通过；诊断脚本真实执行两次，最终版完成 21 次 TTS、21 次短句 ASR、20 次前缀 ASR、4 轮 LLM；Ruff 检查通过。没有进行浏览器麦克风自动化、人耳盲听评分、物理扬声器计时或长时间压力测试，因此不报告主观质量提升或端到端优化收益。本次保持生产参数不变。
